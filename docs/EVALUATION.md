# 품질 평가와 개선 루프

## 실행 순서

`SPEC 승인 → Builder 최초 구현 → Critic 평가 → QA 검증 → Optimizer 개선 → Critic·QA 재검증`

최초 구현 평가는 회차 0이다. 게이트 미달일 때 Optimizer의 첫 수정부터 개선 회차 1로 세며 최대 5까지 허용한다. 각 회차의 점수, 이슈, 테스트 결과, 변경, 잔여 위험을 `PROGRESS.md`에 기록한다. 개선 후 Critic은 전체 점수표와 핵심 흐름을 다시 평가하고, QA는 수정 항목과 전체 필수 회귀 세트를 다시 검증한다. 5회차 재검증 뒤에는 추가 개선 회차를 열지 않는다.

## 역할과 승인 권한

| 활동 | 책임 역할 | 권한 경계 |
|---|---|---|
| 범위·SPEC 승인 | Product Owner | 코드·점수·테스트 결과를 대신 만들지 않음 |
| 기술 설계 승인 | Architect | 구현 완료나 품질 PASS를 선언하지 않음 |
| 최초 구현 | Builder | 자신의 결과를 평가하거나 `DONE` 승인하지 않음 |
| UX/UI 질문·점수·우선순위 | Critic | 코드와 테스트를 수정하지 않음 |
| 객관적 테스트·게이트 증거 | QA | 제품 코드를 수정하거나 실패를 통과 처리하지 않음 |
| 평가 이후 제품 코드·테스트 수정 | Optimizer | 점수·QA 결과·최종 상태를 스스로 승인하지 않음 |
| 최종 상태 기록 | Product Owner | Critic 점수와 QA 증거가 모두 충족될 때만 `DONE` |

Builder는 회차 0의 최초 구현과 평가 전 발견한 명백한 빌드 불가 상태까지만 수정한다. Critic 또는 QA가 최초 평가 결과를 게시한 뒤의 제품 코드·테스트 수정은 Optimizer만 수행한다. 문서 기록, 평가표 작성, 테스트 실행은 코드 수정으로 보지 않는다.

## 100점 평가표

| 영역 | 세부 기준 | 배점 |
|---|---|---:|
| 핵심 기능과 정확성 | 수용 기준 충족 / 대표·경계 결과 정확성 / 입력 검증 | 10 / 10 / 5 |
| 사용성·정보 구조 | 목적 발견 / 흐름 효율 / 상태 피드백 / 오류 복구 | 5 / 5 / 5 / 5 |
| 모바일 반응형 | 레이아웃 / 터치 조작 / 긴 콘텐츠·회전 대응 | 5 / 5 / 5 |
| 접근성 | 키보드·focus / 시맨틱·label / 대비·동적 알림 | 5 / 5 / 5 |
| 성능·안정성 | 진입·상호작용 응답 / 런타임 안정성 / 자원 정리 | 4 / 3 / 3 |
| 다국어·콘텐츠 | 번역 완결성 / 의미 / 형식·잘림 | 2 / 2 / 1 |
| SEO·공유 가능성 | 독립 URL·metadata / canonical·hreflang / 인덱싱 가능한 설명 | 2 / 2 / 1 |
| 개인정보·보안 | 로컬 처리·전송 공개 / 입력·출력 안전성 | 3 / 2 |

각 세부 기준은 `충족=배점 100%`, `부분 충족=배점 50%`, `미충족 또는 NOT TESTED=0점`으로 계산하고 0.5점 단위 합계를 사용한다. 부분 충족과 감점에는 관찰 증거, 재현 절차, 기대 결과를 붙인다. 근거 없는 만점은 허용하지 않는다. 점수는 사용성 완성도를 나타내며 아래 이슈 게이트와 별도로 적용한다.

## 이슈 등급

- `Critical`: 데이터 유출/손실, 보안 문제, 핵심 기능 전면 불가, 잘못된 결과가 중대한 피해를 유발
- `High`: 주요 흐름 불가, 대표 모바일 환경 또는 locale 사용 불가, 심각한 접근성 차단, 반복 크래시
- `Medium`: 우회 가능한 기능·사용성 문제, 일부 엣지케이스 오류, 뚜렷한 성능 저하
- `Low`: 사소한 시각·문구 일관성 또는 비차단 개선

## Critic 사전 질문 규칙

Critic은 결과를 보기 전에 기능별 품질 질문을 최소 10개 작성한다. 질문은 핵심 성공, 첫 사용자 이해, 입력 오류, 결과 신뢰, 모바일, 키보드/스크린 리더, 느린/실패 상태, 다국어, 개인정보, 재사용 흐름을 포함해야 한다. 질문과 답변, 근거, 점수를 평가 기록에 남긴다.

## QA 최소 매트릭스

- 정상 흐름, 빈 값, 최소/최대/초과 값, 잘못된 형식, 반복 실행, 초기화
- 320/375/768/1280px, portrait/landscape가 의미 있는 경우 양쪽
- 현재 지원 기준은 최신 안정 Chrome 계열이다. 기능이 특정 Web API에 의존하면 Architect가 SPEC에 추가 브라우저와 fallback 기준을 명시한다.
- 키보드 전용, focus 순서, 스크린 리더가 인지할 label/상태
- `ko`, `en`, `ja` 라우팅·문구·metadata
- 새로고침, 직접 URL 진입, 뒤로/앞으로 이동
- Console Error 0, 처리되지 않은 Promise rejection 0
- SPEC 승인 때 Product Owner·Architect·QA가 필수 검사 명령과 테스트 목록을 확정한다. 최소 기준은 lint, type-check, build, 도메인 로직 단위 테스트, 핵심 흐름 자동 테스트이며 도구 부재로 실행할 수 있는 항목은 구현 전에 테스트 기반을 범위에 포함한다.

## 게이트별 PASS 정의

- `자동 테스트 PASS`: SPEC의 필수 명령이 종료 코드 0이고 필수 케이스에 fail, skip, todo가 없다. 테스트 목록 변경은 Product Owner와 QA가 이유를 승인해야 한다.
- `Console Error 0`: `ko/en/ja`의 정상·대표 오류 흐름에서 console error와 처리되지 않은 rejection이 한 건도 없다. 의도된 오류도 콘솔에 기록되면 미달이다.
- `모바일 PASS`: 320/375/768/1280px 각각에서 핵심 흐름 완료, 의도하지 않은 가로 스크롤·잘림·겹침 0, 주요 터치 대상 조작 가능, Critical/High 모바일 이슈 0을 모두 만족한다.
- `수용 기준 PASS`: 각 수용 기준에 적어도 하나의 QA 케이스와 실행 증거가 연결되어 있다.
- `NOT TESTED` 또는 `BLOCKED`: 어떤 게이트에서도 PASS로 간주하지 않는다.

Critic과 QA가 같은 현상에 서로 다른 등급을 부여하면 더 높은 등급을 임시 적용한다. 낮추려면 두 역할이 동일한 재현 증거와 사용자 영향에 합의하고 변경 이유를 기록해야 한다.

## 최종 판정

`DONE`은 Critic 점수 ≥90, 통합 이슈 목록의 Critical=0·High=0, QA의 자동 테스트 PASS·Console Error 0·모바일 PASS·수용 기준 PASS를 모두 만족할 때만 가능하다. Product Owner는 이 증거를 확인해 상태를 기록할 뿐 결과를 재평가하지 않는다. 5회차 재검증 후 미달이면 `NEEDS HUMAN REVIEW`로 설정하고 미달 기준, 열린 이슈, 시도 내역, 사용자 영향, 권고 결정을 기록한다. 테스트 불가나 미실행은 PASS가 아니다.
