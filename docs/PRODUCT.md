# 제품 운영 규칙

## 대상 사용자와 핵심 가치

빠르게 단일 작업을 끝내려는 모바일·데스크톱 사용자가 대상이다. 설치, 가입, 업로드 대기 없이 입력하고 즉시 결과를 얻는 것이 핵심 가치다.

## 기능 우선순위

Product Owner는 아래 항목을 각각 1~5점으로 평가한다.

- 사용자 빈도와 문제의 명확성
- 브라우저 단독 처리 가능성
- 구현·유지보수 단순성
- 검색 수요 및 독립 URL 가치
- 기존 공통 컴포넌트 재사용성
- 개인정보 보호 이점

총점이 높아도 서버, 계정, 지속 저장이 필요하면 별도 검토한다. 한 사이클에는 하나의 도구만 `BUILDING` 상태로 둔다.

## 기능 SPEC 필수 항목

구현 전 Product Owner가 다음을 확정한다.

1. 문제 정의와 대상 사용자
2. 한 문장 가치 제안
3. 포함 범위와 제외 범위
4. 대표 사용자 흐름
5. 입력, 출력, 유효성 규칙, 오류 상태
6. 최소 5개의 검증 가능한 수용 기준
7. 모바일, 접근성, 다국어 요구사항
8. URL slug와 언어별 SEO 제목·설명 방향
9. 개인정보 처리와 클라이언트/서버 경계
10. 테스트해야 할 엣지케이스

SPEC 변경은 Product Owner가 승인하고 `PROGRESS.md`에 이유와 영향을 기록한다. Builder가 임의로 범위를 넓히지 않는다.

## 범위 통제

- 현재 수용 기준에 필요하지 않은 아이디어는 구현하지 않고 `IDEAS.md`로 이동한다.
- “있으면 좋음”은 릴리스 차단 조건이 아니다.
- 공통화는 두 곳 이상의 확정된 사용처 또는 명백한 유지보수 이점이 있을 때만 한다.
- 외부 API, 업로드 서버, 데이터베이스는 브라우저 대안이 없고 제품 가치가 비용·개인정보 위험보다 클 때만 제안한다.

## 릴리스 판단

Product Owner는 범위 충족을 확인하고, Critic과 QA가 제공한 근거를 대조해 최종 상태만 결정한다. Product Owner는 테스트를 대신 수행하거나 점수·이슈 등급·PASS 결과를 임의로 변경할 수 없으며, Builder와 Optimizer도 최종 승인할 수 없다. 게이트가 모두 충족되면 `DONE`, 개선 기회가 남았으면 `IMPROVING`, 5회차 재검증 후에도 미달이면 `NEEDS HUMAN REVIEW`로 판정한다. 이 상태에서는 미달 항목, 시도한 개선, 남은 위험과 필요한 결정을 명시한다.
