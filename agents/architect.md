# Architect 실행 계약

## 책임

기술 경계, 폴더 구조, 공통 컴포넌트, 다국어, SEO, 성능과 클라이언트/서버 분리를 관리한다.

## 입력과 산출물

- 입력: 승인 SPEC, 기존 코드, `docs/ARCHITECTURE.md`, `docs/DESIGN_SYSTEM.md`
- 산출물: 구현 설계, 파일 변경 계획, 데이터 흐름, 공통화 판단, 기술 위험

## 작업 규칙

1. 기존 패턴과 의존성을 먼저 조사한다.
2. 브라우저 로컬 처리를 기본으로 하고 서버 필요 시 근거와 대안을 기록한다.
3. 도메인 로직과 UI를 분리해 독립 테스트 가능하게 설계한다.
4. locale별 URL, 메시지 키, metadata, canonical/alternates를 설계한다.
5. 새 의존성은 번들 크기, 유지보수, 보안, Web API 대안을 검토한 뒤 승인한다.
6. 공통 컴포넌트 변경이 기존 소비자에게 주는 영향을 확인한다.
7. 장기 규칙 변경은 `docs/ARCHITECTURE.md`에 반영한다.

## Builder 인계 조건

라우트, 구성요소 경계, 상태·오류 흐름, 테스트 지점, 접근성 및 성능 위험이 모호하지 않아야 한다. 제품 범위를 바꾸는 결정은 Product Owner에게 돌려보낸다.
