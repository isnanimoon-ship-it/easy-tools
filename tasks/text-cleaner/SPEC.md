## 0. 목적과 성공 정의

웹페이지·문서·PDF·AI 답변·엑셀·메모장 등에서 복사한 텍스트를 한 페이지에서 빠르게 정리한다. 핵심 기능은 ①공백/줄바꿈 정리, ②중복 줄 제거 두 가지이며, 별도 페이지로 나누지 않고 하나의 도구 안에서 옵션으로 제공한다.

- 모든 처리는 브라우저에서 수행하고 서버로 전송하지 않는다.
- 원본 입력은 수정하지 않으며 결과는 별도 영역에 표시한다.
- 여러 옵션을 동시에 켜도 결과가 **항상 예측 가능**해야 한다 — 이를 위해 내부 처리 순서(pipeline)를 고정하고 이 문서에 명시한다(§7).
- 맞춤법·띄어쓰기 교정 도구로 오해시키지 않는다 — 이 도구는 문자 구조와 줄 구조만 정리한다.
- 사용자가 "어떤 옵션 때문에 이 줄이 사라졌는지" 이해할 수 있어야 한다.

## 1. 대상 사용자와 주요 사용 사례

- 웹페이지·문서·PDF에서 복사한 텍스트의 불필요한 공백·줄바꿈을 정리하려는 사용자
- AI 챗봇 답변을 다른 곳에 붙여넣기 전에 다듬으려는 사용자
- 엑셀·메모장에서 복사한 목록의 중복 항목을 제거하려는 사용자
- 여러 소스에서 모은 목록(이메일 주소, 키워드, ID 목록 등)을 합치고 중복을 정리하려는 사용자

## 3. 확정 사용자 흐름

1. 원본 textarea에 텍스트를 붙여넣거나 입력한다. 입력 중 글자 수·전체 줄·빈 줄 통계를 실시간으로 보여준다.
2. 필요하면 상단의 Quick Preset을 눌러 옵션을 한 번에 채운다.
3. 공백·줄바꿈 옵션과 중복 옵션을 확인·조정한다. 옵션을 바꿀 때마다(디바운스 후) 결과가 자동 갱신된다.
4. 결과 영역에서 정리된 텍스트와 통계를 확인한다. 결과는 편집 가능하지만, 옵션을 다시 바꾸면 재계산된 값으로 덮어써진다는 점을 항상 눈에 보이게 안내한다.
5. Copy로 복사하거나(Should Have: Download로 .txt 저장) 사용한다.
6. Reset으로 원본·옵션을 초기화한다.

빈 입력은 오류가 아니다. 결과 영역은 입력이 없으면 빈 상태를 보여준다.

## 5. 입력·결과 영역

- 입력: 대용량 textarea, 한글/영어/일본어/Emoji/특수문자/여러 줄/매우 긴 텍스트 지원.
- 결과: **편집 가능한 textarea**(Product Owner 권고 채택). 사용자가 결과를 직접 수정한 뒤 옵션을 하나라도 바꾸면, 수정한 내용은 재계산된 결과로 **덮어써진다** — 이 동작 자체는 의도된 것이지만, 결과 영역을 수동으로 수정한 직후에는 "옵션을 바꾸면 지금 수정한 내용이 사라집니다"라는 안내를 결과 영역 근처에 표시해 예상치 못한 손실을 막는다(Architect 결정 10).
- 결과 textarea에 `aria-live` 상시 적용은 피한다(값이 자주 바뀌어 스크린 리더가 과도하게 읽음) — 대신 통계 영역에 `role="status"`로 완료를 알린다.

| Preset | 적용 옵션 |

| 기본 정리 | 연속 공백→1개, 줄 앞뒤 공백 제거, 연속 빈 줄 최대 1개 |
| 빈 줄 제거 | 줄 앞뒤 공백 제거, 모든 빈 줄 제거 |
| 중복 제거 | 중복 줄 제거(첫 번째 유지, 원래 순서 유지) |
| 한 줄로 만들기 | 한 줄로 합치기(줄바꿈→공백, 연속 공백→1개, 앞뒤 공백 제거) |
| 완전히 정리 | 연속 공백→1개, 줄 앞뒤 공백 제거, 모든 빈 줄 제거, 중복 줄 제거, 중복 비교 시 앞뒤 공백 무시 |

## 7. Architect 결정 1·2 — Pipeline 순서와 각 옵션의 실행 단계

**여러 옵션이 동시에 켜져도 결과가 항상 같은 규칙으로 나오도록, 아래 순서를 고정하고 Builder가 임의로 바꾸지 않는다.**

| 단계 | 이름 | 대상 옵션 | 비고 |
|---|---|---|---|
| 1 | 줄바꿈 정규화 | (항상 실행) | CRLF/CR/LF를 전부 내부 canonical `\n`(LF)으로 통일. 다른 모든 줄 단위 처리의 전제조건이므로 항상 가장 먼저 실행한다 |
| 2 | 특수 공백 변환 | Tab→공백(N칸), NBSP/전각공백→일반공백(Should Have) | 값을 "일반 공백(U+0020)"으로 바꿔 놓아야 이후 3·4단계가 동일한 문자만 다루면 된다 |
| 3 | 줄 앞뒤 공백 제거 | 각 줄 trim | 켜져 있을 때만 |
| 4 | 연속 공백 정리 | `/ {2,}/g → ' '` | **오직 일반 space(U+0020)만** 대상으로 한다. `\s`나 정규식으로 뭉뚱그리면 줄바꿈까지 지워지므로 반드시 공백 문자 하나만 지정한다 |
| 5 | 빈 줄 처리 | 유지/연속 최대 1개/모두 제거 | 3·4단계 이후의 줄 배열에 대해 수행(빈 줄 여부는 trim 결과 기준으로 판단) |
| 6 | 한 줄로 합치기 | "한 줄로 합치기" 옵션 | 활성화 시, 5단계까지 처리된 줄 배열을 **`join(' ')`이 아니라 원본 문자열에 `/\n+/g → ' '`를 적용**한다. 낱줄 join 대신 이렇게 하는 이유: 빈 줄이 남아있으면 `\n+`(1개 이상 연속)를 한 번에 공백 1개로 바꿔야 이중 공백이 생기지 않는다(§7 하단 "구현 함정" 참고). 이 옵션이 켜지면 7~9단계(중복 비교·제거)는 **비활성화**한다 — 한 줄만 남은 텍스트에서 "중복 줄"은 의미가 없다(Architect 결정, Critic 질문 7과 직결) |
| 7 | comparisonKey 생성 | 중복 옵션 전체(§8) | cleanedLine(1~5단계 결과)을 기반으로, 켜진 비교 옵션만 추가로 적용해 별도 문자열을 만든다. cleanedLine 자체는 바꾸지 않는다 |
| 8 | 중복 제거 | 중복 줄 제거 on/off, 첫 번째/마지막 유지 | comparisonKey가 같은 줄들 중 규칙에 따라 하나만 남긴다 |
| 9 | 결과 생성 | — | cleanedLine들을 `\n`으로 합쳐 최종 문자열 생성. 다운로드 시에만 Should Have로 CRLF 변환 |

### 구현 함정 — "한 줄로 합치기" 이중 공백 버그

`텍스트.split('\n').join(' ')` 방식으로 구현하면, 원본에 빈 줄(연속 `\n\n`)이 있을 때 그 자리에 공백이 **두 개 이상** 남는다(각 `\n`이 개별적으로 공백 하나씩 되므로). 이를 막기 위해 6단계는 반드시 `text.replace(/\r?\n+/g, ' ')`처럼 **연속된 줄바꿈을 한 번에** 공백 하나로 치환해야 한다. 이 문서에 명시하지 않으면 Builder가 놓치기 쉬운 지점이라 별도로 강조한다.

### comparisonKey는 cleanedLine과 분리한다(Architect 결정 4)

`comparisonKey`는 `cleanedLine`에 아래를 **추가로** 적용해 만들며, cleanedLine 자체나 최종 출력에는 영향을 주지 않는다.

1. Unicode NFC 정규화(Should Have, 기본 OFF — Architect 결정 5)
2. 대소문자 무시가 켜져 있으면 `toLowerCase()`(로케일 비의존적 처리로 충분 — 한/중/일 텍스트는 대소문자 개념이 없어 영향받지 않는다)
3. 앞뒤 공백 무시가 켜져 있으면 comparisonKey에 한해 trim(출력 옵션 3단계와 별개로, 출력 trim이 꺼져 있어도 비교에서만 무시 가능해야 하므로 독립적으로 적용)
4. 연속 공백 차이 무시가 켜져 있으면(Should Have) comparisonKey에 한해 `/ {2,}/g → ' '`

이 순서(NFC → 대소문자 → trim → 공백 축소)를 고정한다. 자료 구조:

```ts
type LineRecord = {
  originalLine: string;
  cleanedLine: string;
  comparisonKey: string;
  originalIndex: number;
};
```

## 8. Architect 결정 3 — 빈 줄 처리 UI

Radio(또는 동등한 단일 선택 UI)로 3개 중 하나만 고르게 한다 — 브리핑 원안 그대로 채택한다. 체크박스로 만들면 "유지"와 "모두 제거"를 동시에 켜는 모순 상태가 가능해지므로 반드시 단일 선택 구조를 강제한다.

- 빈 줄 판정 기준: 3단계(trim) 이후 길이가 0인 줄.
- 중복 제거 단계에서는 **별도의 "빈 줄 무시" 옵션을 만들지 않는다**(브리핑 §8-4 권고 채택). 빈 줄 처리가 "유지"나 "연속 최대 1개"로 남아있는 상태에서 중복 제거까지 켜면, 남은 빈 줄들도 comparisonKey `""`가 같은 일반 줄로 취급되어 중복 제거 대상이 될 수 있다 — 이는 버그가 아니라 "빈 줄을 특별 취급하지 않는다"는 단순화의 자연스러운 결과이며, 이 문서와 도움말 문구에 명시한다.

## 9. Architect 결정 6 — 중복 유지 방식(첫 번째/마지막)

- **첫 번째 유지(기본, Must Have)**: `Map<comparisonKey, LineRecord>`를 순서대로 순회하며 키가 없을 때만 삽입(있으면 skip). Map은 최초 삽입 순서를 유지하므로 그대로 순회해 출력하면 원래 순서가 보존된다. O(n).
- **마지막 유지(Should Have)**: 순회하며 키가 있어도 **덮어쓴다**(최신 값으로 갱신). Map은 키의 최초 삽입 위치를 유지하지만 값은 마지막 것이 되므로, 이 상태로 그냥 출력하면 "표시되는 줄의 내용은 마지막 값인데 위치는 최초 등장 위치"가 되어 버린다 — 그건 사용자가 기대하는 "마지막 유지"가 아니다. 그래서 마지막 유지 모드에서는 Map을 다 순회한 뒤 **`originalIndex` 기준 오름차순으로 재정렬**해서 출력한다(각 값의 `originalIndex`는 마지막 등장 시점의 인덱스로 덮어써져 있으므로, 정렬하면 "마지막으로 등장한 위치" 기준의 자연스러운 순서가 된다).

두 모드 모두 O(n) 또는 O(n + k log k)(k=고유 키 수)이며 O(n²) 비교를 피한다(§20 요구사항).

## 10. Architect 결정 7·8 — 대용량 입력 기준과 Web Worker

- 텍스트 줄 분리(`split('\n')`), 옵션별 regex/trim, `Map` 기반 중복 제거는 전부 순수 문자열/배열 연산이라 이미지 픽셀 처리보다 훨씬 가볍다. **V1은 Web Worker 없이 main thread**에서 처리한다.
- 입력 크기 기준(Architect 잠정값, Builder 실측 후 §29에 확정 기록):
  - 하드 제한: 10 MB(문자 기준 약 1,000만자). 초과 시 "텍스트가 너무 큽니다" 오류를 표시하고 처리를 시작하지 않는다.
  - 성능 경고 기준: 2 MB 또는 50,000줄 중 먼저 도달하는 쪽. 초과 시 하드 차단은 아니지만 "큰 텍스트는 처리가 느릴 수 있습니다"를 안내하고, 실시간(디바운스) 자동 처리 대신 debounce를 늘리거나 수동 "정리 적용" 버튼으로 전환하는 것을 Should Have로 검토한다(§11 debounce 정책과 연결).
  - 목표: 100,000줄(§20 성능 테스트 기준)에서도 main thread 그대로 수 초 이내에 완료. Builder가 실측해 목표 미달이면 Worker 도입을 재검토한다(억지로 Must Have를 낮추지 않는다).

## 11. Architect 결정 9 — 실시간 처리 debounce

- 기본 debounce: **200ms**(입력/옵션 변경 모두 동일 적용).
- §10의 "성능 경고 기준"(2MB 또는 50,000줄) 이상인 입력에서는 debounce를 **500ms**로 늘린다.
- 하드 제한(10MB) 이상은 애초에 처리를 시작하지 않으므로 debounce와 무관하다.
- 정확한 값은 튜닝 대상이며 Builder가 실제 입력으로 체감 지연을 확인한 뒤 §29에 최종값을 기록한다.

## 12. Architect 결정 10 — 결과 편집 허용과 재계산 충돌 안내

§5에서 정한 대로 결과 textarea는 편집 가능하다. 사용자가 결과를 직접 편집하면 내부적으로 "수동 편집됨" 플래그를 켜고, 그 상태에서 옵션을 변경하면:

1. 재계산된 값으로 결과를 갱신한다(Product Owner 방침 — 옵션은 항상 "지금 옵션 기준 결과"를 보여줘야 하므로).
2. 단, 그 직전까지 "수동 편집됨" 상태였다면, 결과가 방금 옵션 변경으로 덮어써졌다는 사실을 짧게 안내한다(예: 결과 영역 상단에 일시적 알림 문구).
3. 원본 입력을 바꾸거나 옵션을 바꾸지 않는 한(즉 사용자가 결과만 계속 편집하는 동안) 자동 재계산으로 편집 내용을 지우지 않는다.

## 13. Architect 결정 11 — Preset과 세부 옵션의 관계

- Preset 버튼을 누르면 해당 프리셋에 정의된 옵션 값 전체로 하위 옵션 상태를 덮어쓰고, 그 Preset 버튼을 "선택됨"으로 표시한다.
- 이후 사용자가 하위 옵션 **아무거나 하나라도** 바꾸면, 현재 상태가 더 이상 그 Preset과 정확히 일치하지 않으므로 "선택됨" 표시를 해제한다(어떤 Preset도 활성 표시하지 않는 "커스텀" 상태로 전환). 이 로직은 옵션 상태를 Preset 정의와 얕은 비교(shallow compare)하는 방식으로 구현할 수 있다.
- Preset은 하위 옵션을 "숨기지" 않는다 — 항상 아래에 그대로 보이고 편집 가능하다(브리핑 요구사항 그대로).

## 14. Architect 결정 12 — 통계 계산 방식

- **글자 수는 `[...text].length`(코드 포인트 기준)로 계산한다.** 단순 `string.length`(UTF-16 code unit)는 이모지·서로게이트 쌍을 2글자로 잘못 세므로 사용하지 않는다.
- "줄"은 줄바꿈 정규화(1단계) 이후 `\n` 기준으로 분리한 개수.
- 기본으로 보여주는 지표(과도한 숫자 나열 금지 원칙 준수):
  - 원본 줄, 결과 줄, 제거된 줄(= 원본 줄 − 결과 줄), 원본 글자 수, 결과 글자 수
  - 중복 제거가 켜져 있을 때만 추가: 고유 줄, 중복(제거된) 줄
- **"한 줄로 합치기"가 켜져 있으면 줄 기반 통계(원본 줄/결과 줄/제거된 줄)를 숨기고 글자 수 통계만 보여준다** — 결과가 항상 1줄이라 줄 통계가 의미 없기 때문이다.
- "빈 줄 제거 몇 개", "기타 정리 몇 자" 같은 세부 breakdown은 V1에 넣지 않는다 — 어떤 연산이 몇 자를 지웠는지 추적하려면 파이프라인 각 단계마다 diff를 계산해야 해서 복잡도가 크게 늘고, 브리핑 자체도 "과도하게 많은 숫자를 한 번에 보여주지 않는다"고 명시했다. 필요하면 Should/Could Have로 별도 승인 후 추가한다.

## 15. Architect 결정 13 — NBSP / 전각 공백(U+3000) 처리 정책

- **기본값 OFF**(Should Have, opt-in). 켜면 2단계(특수 공백 변환)에서 NBSP(U+00A0)와 IDEOGRAPHIC SPACE(U+3000)를 일반 공백(U+0020)으로 바꾼 뒤, 이후 4단계(연속 공백 정리)가 자연스럽게 함께 정리한다.
- 기본이 OFF인 이유: 일부 문서(특히 인쇄용 조판이나 특정 웹페이지)는 줄바꿈 방지 목적으로 NBSP를 의도적으로 쓴다 — 기본으로 다 지워버리면 사용자가 원하지 않는 변경이 조용히 일어날 수 있다.
- 참고로 JavaScript의 `String.prototype.trim()`과 정규식 `\s`는 이미 NBSP·U+3000을 공백으로 취급한다. 따라서 "줄 앞뒤 공백 제거"(3단계, trim 기반)는 이 옵션과 무관하게 이미 NBSP로 시작/끝나는 줄도 정리한다 — 이 옵션은 어디까지나 **줄 중간에 남아있는** NBSP/전각공백을 일반 공백으로 바꾸는 것이 목적이다. 이 차이를 SPEC과 도움말에 명확히 적는다.
- Zero-width 문자(ZWSP, ZWJ 등)는 자동 제거하지 않는다(브리핑·Do Not Build 명시 그대로 유지).

## 16. Architect 결정 14 — 다운로드 줄바꿈 형식

- 내부 처리는 항상 LF(`\n`) 기준(§7).
- 다운로드(Should Have)는 기본 LF로 저장한다 — 내부 canonical 형식과 일치시켜 변환 단계를 하나 줄이고, Windows 10 이후 메모장도 LF를 정상 처리한다.
- CRLF 저장은 Should Have로 선택 옵션을 제공한다(다운로드 시점에만 `\n` → `\r\n` 치환, 내부 상태는 건드리지 않는다).
- 파일명: 기본 `cleaned-text.txt`. 결과 유형이 "고유 줄"이 아닌 다른 값(중복된 값만/한 번만 등장, Should Have)일 때는 `unique-lines.txt`로 고정하지 않고 유형에 맞는 이름(`duplicate-lines.txt`, `unique-once-lines.txt`)을 쓴다 — 하나의 이름으로 통일하면 사용자가 어떤 파일을 받았는지 헷갈릴 수 있다.

## 17. 결과 유형(Should Have)

중복 제거가 켜졌을 때만 노출되는 선택지. 기본은 "고유 줄".

| 유형 | 정의 |
|---|---|
| 고유 줄(기본) | comparisonKey 기준으로 중복을 제거한 전체 결과(Must Have 기본 동작과 동일) |
| 중복된 값만 | comparisonKey가 2회 이상 등장한 값들만(1회 표시) |
| 한 번만 등장한 값 | comparisonKey가 정확히 1회만 등장한 값들만 |

세 유형 모두 원래 순서를 유지한다(등장 순서 기준 첫 원본 위치).

## 18. 중복 항목 보기(Should Have)

- comparisonKey별 등장 횟수를 내림차순으로 보여준다. 항목이 많을 때는 상위 N개(예: 50개)만 먼저 보여주고 "더 보기"로 펼친다.
- 항목 클릭 시 해당 comparisonKey의 원본 등장 줄 번호(originalIndex+1) 목록을 보여준다.
- OCR·QR 같은 콘텐츠가 아니므로 개인정보 우려는 적지만, 사용자가 붙여넣은 원문 일부가 그대로 노출되는 기능이라는 점은 인지하고 있어야 한다(별도 안전장치는 필요 없음 — 애초에 로컬에서만 보여주는 사용자 자신의 텍스트다).

## 28. Architect 최종 검토

### 기존 구조와의 충돌

- Next.js App Router, TypeScript, Tailwind, next-intl, 독립 locale URL 구조와 일치한다.
- Server page + Client tool + 순수 domain module(`pipeline.ts`) 구조로 기존 아키텍처와 충돌하지 않는다.
- 서버 route나 데이터베이스가 필요 없고, 이미지 처리 도구들과 달리 Canvas/decode 관련 제약도 없다 — 순수 문자열 처리라 구조가 가장 단순한 축에 속한다.
- 외부 의존성 추가 없음.

### 확정된 14개 결정

1. Pipeline 순서: 줄바꿈 정규화 → 특수공백 변환 → 줄 trim → 연속공백 정리(공백 전용) → 빈 줄 처리 → 한 줄 합치기(`\n+`→' ' 한 번에 치환) → comparisonKey 생성 → 중복 제거 → 결과 생성
2. 각 옵션의 실행 단계: §7 표로 확정. 한 줄 합치기 활성 시 중복 관련 단계는 비활성화
3. 빈 줄 처리 UI: Radio 3택 1, 중복 단계에는 별도 빈 줄 옵션을 만들지 않음(자연스러운 부작용 문서화)
4. comparisonKey: cleanedLine 기반, NFC→대소문자→trim→공백축소 순으로 추가 적용, 출력에는 영향 없음
5. NFC 비교 기본값: OFF(opt-in)
6. 첫 번째 유지: Map 삽입-스킵 방식. 마지막 유지: Map 덮어쓰기 후 originalIndex 재정렬
7. 대용량 기준(잠정): 하드 제한 10MB, 성능 경고 2MB/50,000줄, Builder 실측 후 §29 확정
8. Web Worker: V1 미도입, main thread. 실측 후 목표 미달 시 재검토
9. debounce: 기본 200ms, 대용량 시 500ms
10. 결과 편집: 허용. 옵션 변경 시 재계산이 덮어쓴다는 점을 수동 편집 직후 안내
11. Preset: 하위 옵션을 값으로 채우고 계속 노출·수정 가능. 옵션을 하나라도 바꾸면 "선택됨" 표시 해제
12. 통계: `[...text].length` 코드포인트 기준, 지표 5종(+중복 2종), 한 줄 합치기 시 줄 통계 숨김
13. NBSP/U+3000: 기본 OFF, 켜면 2단계에서 일반 공백으로 치환(trim은 이미 NBSP를 인식함을 문서화)
14. 다운로드 줄바꿈: 기본 LF, CRLF는 Should Have 선택 옵션

### 남은 구현 위험과 통제

- "한 줄로 합치기"의 이중 공백 함정(§7)은 실제로 흔히 나는 실수라 QA 항목(10번)으로 명시적으로 고정했다.
- 마지막 유지 모드의 재정렬 로직(§9)은 첫 번째 유지보다 복잡해 별도 unit 테스트가 필요하다.
- 대용량 처리 성능은 Architect가 추정만 했을 뿐 실측이 아니다 — Builder 실측 없이 §27 완료 조건을 PASS 처리할 수 없다.
- 옵션 조합이 많아(공백 5종 이상 × 중복 5종 이상) 전수 조합 테스트는 불가능하다 — §24의 대표 조합 1개를 최소 회귀로 고정하고, Critic 질문 7("잘못된 조합으로 예상 못한 결과")을 QA가 추가로 자유탐색한다.
