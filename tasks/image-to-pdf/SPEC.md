# 이미지 → PDF 변환기 SPEC

## 문서 상태

- 상태: `구현 완료 — 핵심 자동 QA PASS, 저사양 기기·인쇄 검토 대기`
- 작성: 2026-09-13
- 예정 URL: `/{locale}/tools/image-to-pdf`
- 범위: Product Owner 요구사항, Architect 검토, Builder 구현 및 QA 기록. 배포·푸시는 별도 요청 전까지 하지 않는다.

## 1. 목적과 사용자

JPG·PNG·WebP 사진이나 스캔 이미지를 한 장 또는 여러 장 선택해, 순서를 정하고 하나의 PDF로 저장한다. 보고서 첨부, 서류 제출, 영수증 묶기처럼 이미지 파일을 PDF 형태로 제출해야 할 때 사용한다. 로그인이나 외부 변환 서비스 없이 브라우저에서 처리한다.

PDF는 이미지를 페이지에 배치한 결과다. 이미지 안의 글자가 선택·검색 가능한 텍스트로 바뀌지 않으며 OCR이나 문서 편집 기능은 제공하지 않는다.

## 2. Product Owner 범위 결정

### Must Have — 첫 버전

- JPG/JPEG, PNG, WebP 정적 이미지 업로드. 확장자만 믿지 않고 실제 형식과 디코딩 가능 여부 확인.
- 여러 장 선택, 파일별 썸네일·이름·크기·상태 표시, 개별 삭제, 전체 초기화.
- 페이지 순서 변경. 모바일과 키보드에서도 사용 가능한 위/아래 이동 버튼을 기본으로 한다. 드래그 정렬은 필수가 아니다.
- 기본 설정: A4 세로, 이미지 비율 유지, 페이지 안쪽에 맞춤(contain), 이미지 1장당 PDF 1페이지, 흰 배경. 가로·세로는 사용자가 선택할 수 있다.
- 페이지 크기: A4와 Letter. 원본 이미지 크기에 맞춘 페이지는 첫 버전에서 제외한다.
- 여백: 없음/보통 중 선택. 기본은 보통이며 값은 구현 전에 pt 단위로 확정해 UI에 표시한다. 여백 없음은 인쇄 시 가장자리가 잘릴 수 있음을 안내한다.
- 긴 변과 짧은 변의 비율을 유지하며 이미지 전체가 페이지 안에 들어가도록 배치한다. 임의 잘라내기·늘이기 금지.
- 한 번의 실행으로 하나의 PDF를 만들고 안전한 기본 이름(예: `images-to-pdf.pdf`)으로 다운로드. 원본 파일명·위치 정보는 PDF 파일명으로 복사하지 않는다.
- 빈 목록은 오류가 아닌 초기 상태. 업로드 오류는 해당 파일에 이해하기 쉬운 문구로 표시하고 다른 정상 파일은 유지한다.
- 변환 중 진행 상태·중복 실행 방지·실패 후 재시도 제공. 설정이나 순서 변경 후에는 이전 결과를 무효화한다.
- 모든 처리 클라이언트에서 수행. 이미지 바이트, 파일명, PDF를 서버·외부 API·localStorage·history로 전송하거나 저장하지 않는다. 사이트의 일반 방문 집계가 있다면 파일 내용과 무관함을 확인한다.
- 기존 사이트 UI, 라이트/다크 테마, 공통 상세페이지 구조, `ko/en/ja`, 도구 레지스트리·검색·카테고리·sitemap 규칙에 맞춘다.

### Should Have — 첫 버전 안정화 후

- 드래그 앤 드롭 업로드와 드래그 정렬(위/아래 버튼 대체 불가).
- 출력 품질/용량 선택 및 선택 시 재인코딩 여부·화질 손실 안내.
- 결과 PDF 미리보기. 브라우저 내장 PDF 뷰어 차이를 고려해 다운로드가 동작할 때만 보조 기능으로 제공.
- 사진 EXIF 회전을 처리한 실제 출력 방향과 썸네일 방향 일치 여부를 브라우저별 검증 후 개선.

### Could Have

- 원본 비율 페이지, 여러 이미지 한 페이지에 배치, 페이지마다 다른 방향, 파일명 기반 정렬, 개별 PDF 생성, PDF 메타데이터 편집.

### Do Not Build — 첫 버전

- PDF → 이미지, OCR·검색 가능한 텍스트 PDF, 이미지 속 텍스트 편집, 암호화·전자서명.
- 서버 업로드/저장, URL 이미지 가져오기, 외부 변환 API.
- HEIC/HEIF, RAW, SVG, GIF·APNG·애니메이션 WebP. 애니메이션은 첫 프레임만 몰래 저장하지 않고 지원 불가를 명시한다.
- 입력 이미지를 PDF에 담았다는 이유로 EXIF/GPS가 반드시 제거된다고 보장하는 주장. 출력 방식별 재검증 전까지 메타데이터 삭제 도구로 홍보하지 않는다.

## 3. 핵심 사용자 흐름

1. 이미지를 추가한다. 유효한 파일은 썸네일과 순번을, 실패한 파일은 이유를 보여준다.
2. 위/아래 버튼으로 페이지 순서를 조정하고 필요 없는 파일을 제거한다.
3. A4/Letter, 세로/가로, 여백을 선택한다. 결과 페이지 수와 처리 대상을 확인한다.
4. `PDF 만들기`를 누른다. 처리 중 상태를 보여주고 성공 시 다운로드 버튼을 활성화한다.
5. 설정·순서·파일이 바뀌면 기존 결과는 더 이상 최신 결과가 아님을 명확히 보여주거나 폐기한다.

## 4. 출력 규칙과 제한

- 페이지 순서는 화면 목록 순서와 같고, PDF 페이지 수는 성공적으로 선택된 이미지 수와 같다.
- 각 페이지에서 이미지 전체가 지정 여백 안에 들어가며 원본 종횡비를 유지한다. 빈 공간은 흰색이다. PNG/WebP 투명 영역도 흰 배경에 합성될 수 있음을 안내한다.
- EXIF 방향이 있는 JPEG는 브라우저 디코딩·재인코딩 경로에서 방향이 이중 적용되지 않도록 검증한다. 검증 전에는 모든 방향을 지원한다고 단정하지 않는다.
- 현재 구현은 형식과 회전 처리의 일관성을 위해 모든 이미지를 브라우저 Canvas에 흰 배경으로 그린 뒤 JPEG로 재인코딩해 PDF에 삽입한다. 원본 JPEG 직접 삽입은 사용하지 않으며 출력 파일 크기·화질·투명도가 달라질 수 있다.
- 이미지에 포함된 GPS·작성자 등 메타데이터가 PDF에 남는지 여부는 삽입 경로별 자동 검증 후 문구를 확정한다. 개인정보 제거가 목적이면 기존 사진 메타데이터 삭제 도구를 먼저 사용하도록 안내한다.
- 초기 제안 한도: 최대 20장, 파일당 25 MiB, 이미지당 24 MP, 총 디코딩 픽셀 120 MP. **구현 전 저사양 모바일·브라우저 QA로 확정 또는 하향**한다. 한도를 넘으면 변환 시작 전에 이유와 해결 방법을 제시한다. 출력 PDF의 크기를 입력 합계로 정확히 예측할 수 있다고 주장하지 않는다.
- 메모리 부족, 깨진 이미지, 브라우저가 디코딩하지 못하는 파일, PDF 생성 실패는 앱 전체 오류로 전파하지 않고 복구 가능한 메시지로 처리한다.

## 5. UI·접근성·콘텐츠

- 입력 → 이미지 목록/순서 → 간단한 PDF 설정 → 만들기/다운로드 순서. 모바일 320px에서도 가로 스크롤과 버튼 겹침이 없어야 한다.
- 업로드, 순서 이동, 삭제, 설정, 만들기, 다운로드에 명확한 label·focus 표시 제공. 이미지 썸네일의 대체 텍스트에는 파일명과 순번을 사용한다.
- 오류는 텍스트와 `role="alert"`, 처리 상태는 `role="status"` 등으로 전달하며 색상만으로 구분하지 않는다.
- 상세페이지 설명은 실제 기능을 반영한다: 사용 방법, 이미지 비율·페이지 크기, 투명 배경과 화질, 개인정보 처리, FAQ, 관련 이미지 도구. SEO용 반복 문구를 만들지 않는다.
- 관련 도구 후보: 이미지 용량 줄이기, 사진 메타데이터 삭제, 스크린샷 이어붙이기. PDF → 이미지는 실제 출시 전까지 링크하지 않는다.

## 6. Architect 사전 검토

### 라이브러리 선택

브라우저에서 동작하는 `pdf-lib`를 우선 채택한다. 공식 API는 JPEG/PNG 바이트 삽입, 페이지 생성, 브라우저에서 PDF 저장을 지원하며 라이선스는 MIT다. `jsPDF` 역시 브라우저 이미지 삽입과 MIT 라이선스를 제공하지만, 현재 요구사항은 이미지별 페이지 생성·정확한 크기 계산과 원본 JPEG/PNG 삽입이 중심이므로 `pdf-lib`의 API가 더 직접적이다. 버전·실제 번들 크기·압축 효율은 구현 직전 확인하고 동적 import로 도구 페이지에만 로드한다. WebP는 별도 Canvas 변환이 필요하다. 라이브러리 설치나 코드 변경은 아직 하지 않는다.

근거: [pdf-lib PDFDocument API](https://pdf-lib.js.org/docs/api/classes/pdfdocument), [pdf-lib 프로젝트 및 브라우저 예시](https://github.com/Hopding/pdf-lib), [pdf-lib MIT 라이선스](https://github.com/Hopding/pdf-lib/blob/master/LICENSE.md), [jsPDF 프로젝트](https://github.com/parallax/jsPDF).

### 설계 경계와 위험

- `File` 검증/목록 상태, 이미지 디코딩·방향 처리, PDF 페이지 배치, 다운로드를 분리한다. 기존 이미지 도구의 검증 유틸은 형식·한도가 맞는 부분만 재사용하고 기존 도구 로직을 수정하지 않는다.
- 원본 JPEG 직접 삽입과 브라우저 회전 적용은 동시에 항상 보장되지 않는다. 방향 태그가 있는 파일은 별도 경로로 처리하고 1~8 방향 fixture로 결과를 확인한다.
- WebP 변환은 메모리와 PDF 크기를 늘릴 수 있다. 한 장씩 처리하고 임시 Bitmap/Object URL을 해제한다. 출력이 지나치게 큰 경우 임의 자동 축소 대신 사용자에게 원인을 안내한다.
- `pdf-lib`의 데이터 처리와 PDF 저장은 클라이언트 컴포넌트에서만 실행한다. 서버 액션·API route는 추가하지 않는다.
- PDF가 유효하고 실제 각 페이지를 열 수 있는지는 헤더 검사만으로 충분하지 않다. PDF 파서 또는 브라우저 렌더러로 페이지 수·크기·순서를 검증한다.

Architect 판단: **조건부 적합**. 현재 JPEG 재인코딩 경로로 구현했으며 Chrome에서 회전 1~8의 PDF 내장 이미지 픽셀 방향과 투명 PNG의 흰 배경을 확인했다. 저사양 메모리·다른 브라우저·인쇄 검토는 별도 QA로 남는다.

## 7. QA 필수 매트릭스

- 단일 JPEG, PNG(투명 포함), WebP, 혼합 3장: 생성·페이지 수·순서·다운로드·재열기.
- A4/Letter × 세로/가로 × 여백 없음/보통: 페이지 크기와 이미지 종횡비·잘림 없음 확인.
- 순서 위/아래 이동, 중간 파일 삭제, 전체 초기화, 변경 후 결과 무효화, 반복 생성.
- JPEG EXIF 방향 1~8: 썸네일과 PDF의 표시 방향 비교. 실패 방향은 지원 제외 또는 안전한 보정 구현 후 재검증.
- PNG/WebP 알파 채널: 검정 배경이나 의도치 않은 투명 PDF가 아닌 흰 배경 확인.
- 긴 파일명·한국어/일본어 파일명, 중복 파일명, 빈 선택, 0바이트·손상·위장 확장자·지원 외 형식·애니메이션.
- 파일 수·용량·픽셀 한도의 정상/경계/초과, 저사양 모바일에서 큰 파일 처리·실패 후 복구.
- PDF 페이지 수·페이지 크기·이미지 순서·실제 열림 자동 검증. 파일 서명 `%PDF-`만 확인하는 테스트로 대체하지 않는다.
- 출력 PDF의 메타데이터·GPS 잔존 여부를 입력 형식과 삽입/재인코딩 경로별 확인. 결과에 맞지 않는 개인정보 문구 금지.
- `ko/en/ja`, 라이트/다크, 320/375/768/1280px, 키보드·스크린리더, Console Error 0, 네트워크 요청에 이미지/파일명 유출 0.
- `npm.cmd run lint`, `npm.cmd run type-check`, `npm.cmd test`, `npm.cmd run build`, `docs/EVALUATION.md`의 기존 게이트.

## 8. 완료 조건과 현재 상태

구현 후 모든 Must Have, 위 필수 QA, 기존 평가 게이트를 충족해야 `DONE`이다. 현재 핵심 기능과 자동 QA는 통과했으나 저사양 모바일 메모리·실제 인쇄·크기 경계값 검증이 남아 있어 **최종 DONE은 보류**한다. 자세한 결과는 `QA.md`에 기록한다. 푸시는 별도 요청 전까지 하지 않는다.
