# 한글 초성 변환기 / Korean Initial Consonant Converter SPEC

## 문서 상태

- 상태: `SPEC 작성 + Architect 검토 완료` — 구현 전 (`APPROVED FOR BUILD`)
- 작성일: 2026-08-30
- URL: `/{locale}/tools/korean-initial-converter`
- 지원 locale: `ko`, `en`, `ja`
- 우선순위: P2 신규 도구
- 유일한 구현 기준: 이 문서
- 브리핑: 사용자가 목적·예시·핵심 원칙·UI·QA 목록까지 이미 상세히 지정했다. 이 문서는 그 브리핑을 프로젝트의 SPEC 형식으로 정리하고, 브리핑이 "검토"·"권장"으로 열어 둔 지점들을 Architect가 확정한 것이다.

## 1. 목적과 성공 정의

사용자가 한글 텍스트를 입력하면 각 한글 완성형 음절의 초성만 추출해 **입력 즉시** 결과를 보여준다.

V1의 성공은 다음 흐름을 빠르고 예측 가능하게 완료하는 것으로 정의한다.

`입력 → (디바운스 없이) 즉시 초성 결과 표시 → 필요 시 공백 제거 옵션 → 복사`

- 서버로 어떤 요청도 보내지 않는다.
- 완성형 한글(가~힣)만 초성으로 바꾸고, 그 외 모든 문자(영문·숫자·공백·줄바꿈·이모지·특수문자·이미 분리된 자모·일본어 등 기타 유니코드)는 원문 그대로 둔다.
- 초성 검색기·초성 퀴즈·초성→단어 복원 등으로 범위를 넓히지 않는다.

## 2. 대상 사용자와 주요 사용 사례

- 초성 채팅/댓글(이른바 "초성체")을 만들어 공유하려는 사용자
- 별명·닉네임·이름을 초성으로 가리고 싶은 사용자(단, 이 도구는 개인정보 마스킹 도구가 아니며 그런 용도로 안내하지 않는다 — 단순 텍스트 변환 유틸리티)
- 초성 퀴즈·초성 게임 콘텐츠를 만들 때 원문에서 초성만 빠르게 뽑아 보려는 사용자

## 3. 기능 범위

### Must Have

- 한글 완성형(U+AC00~U+D7A3) 음절의 초성 19자 추출
- 쌍자음(ㄲㄸㅃㅆㅉ) 포함 정확한 초성 매핑
- 영문/숫자 원문 유지
- 특수문자 원문 유지
- 공백/줄바꿈 원문 유지(기본값)
- 이미 분리된 호환 자모(ㄱㄴㅏㅓ 등)와 이모지·기타 유니코드 원문 유지
- 입력 즉시 결과 갱신(실시간, 별도 변환 버튼 없음)
- 결과 복사(Copy)
- 초기화(Reset)
- NFC 정규화 후 변환(원본 입력 문자열 자체는 변경하지 않음)
- 100% 브라우저 처리, 서버 요청 없음

### Should Have

- 공백 제거 옵션(체크박스, 기본값 OFF = 공백 유지)
- 입력/결과 글자 수 표시(코드 포인트 기준, 아주 짧은 한 줄로만)

### Could Have (V1 제외, 후속 검토)

- 특수문자 제거 옵션
- 초성 사이 구분자 삽입 옵션
- 결과 파일 다운로드(.txt)

### Do Not Build (V1)

- 초성 검색기
- 초성 퀴즈 생성기
- 초성 → 단어 복원(사전/AI 추론)
- 사전 검색 연동
- 서버 저장, 로그인, 이력 저장

## 5. Architect 결정 1 — 변환 알고리즘: 순수 함수, 외부 라이브러리 없음

Unicode 오프셋 계산만으로 충분하고 정확하므로 `hangul-js` 류의 외부 라이브러리를 추가하지 않는다.

```ts
const INITIALS = [
  "ㄱ","ㄲ","ㄴ","ㄷ","ㄸ","ㄹ","ㅁ","ㅂ","ㅃ",
  "ㅅ","ㅆ","ㅇ","ㅈ","ㅉ","ㅊ","ㅋ","ㅌ","ㅍ","ㅎ",
] as const; // 19개, 순서 고정

const SYLLABLE_START = 0xac00; // '가'
const SYLLABLE_END = 0xd7a3;   // '힣'
const INITIAL_STRIDE = 588;    // 21(중성) × 28(종성, "없음" 포함)

function toInitial(codePoint: number): string | null {
  if (codePoint < SYLLABLE_START || codePoint > SYLLABLE_END) return null;
  const index = Math.floor((codePoint - SYLLABLE_START) / INITIAL_STRIDE);
  return INITIALS[index];
}
```

- `U+AC00~U+D7A3` 완성형 한글 블록은 11,172자 전부가 빈틈없이 채워져 있다(예외·gap 없음). 범위 검사만으로 안전하다.
- 문자열은 UTF-16 code unit(`.length`, 인덱스 for 루프)이 아니라 **code point 단위**(`[...text]` 또는 `Array.from`)로 순회한다. 완성형 한글은 전부 BMP 안에 있어 이 구분이 한글 처리 자체에는 영향이 없지만, 이모지 등 서로게이트 쌍 문자를 코드 유닛 단위로 자르면 깨진 문자가 섞여 나온다(`text-cleaner`에서 이미 같은 이유로 code point 순회를 채택한 전례가 있다).
- 각 문자는 1:1로 매핑된다 — 초성이면 `INITIALS[index]`로, 아니면 원문 문자 그대로 `join("")`. 문자 사이에 공백을 추가하거나 묶는 로직은 없다. 이 1:1 매핑이 "안녕!" → "ㅇㄴ!"처럼 구두점이 바로 붙는 동작을 자연스럽게 만족시킨다.

## 6. Architect 결정 2 — NFC 정규화 범위: 변환 파이프라인에만 적용, 원본 state는 그대로

브리핑의 권장안(`text.normalize("NFC")`)을 채택하되, 적용 범위를 명확히 한다.

- **입력 textarea가 바인딩하는 React state(`input`)는 사용자가 실제로 타이핑/붙여넣기한 문자열을 그대로 보관한다.** NFC 정규화는 하지 않는다 — 그래야 사용자가 입력을 복사해서 다른 곳에 붙여넣어도 원문이 보존된다.
- **초성 변환 함수에 넘기기 직전에만** `input.normalize("NFC")`를 적용한 사본으로 계산한다. 즉 `convert(input.normalize("NFC"), options)` 형태이며, `input` 자체는 절대 재대입하지 않는다.
- 이렇게 하면 macOS 등에서 들어오는 NFD 분해형 한글(`ᄀ`(U+1100) + `ᅡ`(U+1161) 같은 결합 자모 시퀀스)도 완성형과 동일하게 처리되면서, 입력창에 보이는 원문 텍스트는 사용자가 입력한 그대로 유지된다.

### 기술 명확화: "결합 자모"와 "호환 자모"는 다른 유니코드 블록이다

브리핑은 "이미 분리된 자모"(예: 사용자가 직접 입력한 `ㄱ`, `ㅏ`)와 "NFD 한글"(예: `ᄀ+ᅡ`)을 유사한 개념처럼 나란히 설명하지만, 구현상 정확히 구분해야 한다.

| 구분 | 유니코드 블록 | 예 | NFC 정규화 영향 |
|---|---|---|---|
| 완성형 한글 음절 | Hangul Syllables `U+AC00~U+D7A3` | 가, 나, 강 | 대상(초성 추출) |
| 결합 자모(초성/중성/종성) | Hangul Jamo `U+1100~U+11FF` | ᄀ(U+1100), ᅡ(U+1161) | NFC가 완성형으로 **재결합**시킴 |
| 호환 자모(단독 표시용) | Hangul Compatibility Jamo `U+3131~U+318E` | ㄱ, ㄴ, ㅏ, ㅓ | NFC로 결합되지 않음 — 항상 원문 그대로 통과 |

- 한국어 키보드에서 자음/모음 키를 단독으로 눌러 나오는 `ㄱ`, `ㅏ` 등은 대개 **호환 자모(U+3131 블록)** 이고, 애초에 완성형 범위 밖이라 NFC 여부와 무관하게 항상 원문 그대로 통과한다 — 별도 분기 처리가 필요 없다.
- macOS의 NFD 이슈로 들어오는 것은 **결합 자모(U+1100 블록)** 이며, 이는 NFC 정규화가 정확히 겨냥하는 대상이다. `text.normalize("NFC")` 한 줄로 두 케이스 모두 올바르게 처리된다.
- 결론: Builder는 두 블록을 다르게 다루는 코드를 추가로 작성할 필요가 없다. NFC 정규화 + 완성형 범위 검사만으로 브리핑의 모든 예시(호환 자모 통과, NFD 재조합)가 성립한다. 다만 QA에서는 반드시 두 케이스를 **별도 테스트**로 구분해 검증한다(§10의 QA #12, #13).

## 7. Architect 결정 3 — 공백 제거 옵션의 정확한 범위: 줄바꿈은 보존

브리핑 예시는 한 줄 안의 단어 사이 공백만 보여주고, 여러 줄 입력과의 상호작용은 정의하지 않았다. Architect가 다음과 같이 확정한다.

- "공백 제거" 옵션은 **스페이스류 공백 문자만** 제거한다(일반 space, 그리고 특수 공백이 섞여 들어올 가능성을 감안해 NBSP·전각 공백 포함). **줄바꿈(`\n`, `\r\n`)은 제거 대상이 아니다.**
- 이유: "공백 제거"를 줄바꿈까지 지우는 것으로 해석하면 여러 줄로 입력한 텍스트가 사용자 의도와 무관하게 한 줄로 합쳐지는, 이름과 다른 부작용이 생긴다. "여러 줄 입력도 정상 처리한다"는 Must Have 원칙과 "공백 제거"는 서로 다른 축의 기능이므로 섞지 않는다.
- 이 옵션은 **입력 자체가 아니라 변환 결과 표시 단계**에서만 적용한다 — 입력 textarea의 원문은 항상 그대로 둔다.
- 구현: `mergedResult.replace(/[  　]+/g, "")` 형태(여러 개 연속 공백도 옵션이 켜지면 전부 제거, 남길 이유가 없으므로 "1개로 축소" 같은 중간 단계는 두지 않는다 — text-cleaner의 공백 관련 옵션과 달리 이 도구는 "있다/없다"의 단순 토글이면 충분하다).

## 8. Architect 결정 4 — 실시간 변환과 debounce: 기본 없음, 조건부만

- 변환 함수는 문자 하나당 O(1) 조회로 끝나는 단순 순회이므로 일반적인 입력 길이(수백~수천 자)에서는 매 keystroke마다 동기 계산해도 체감 지연이 없다. **V1은 debounce 없이 `onChange`에서 즉시 재계산한다.**
- 단, QA #15(10만 자 이상 문자열)에서 실제로 입력 지연이 발생하는지 Builder가 실측한다. 만약 100,000자 기준 계산 시간이 한 프레임(약 16ms)을 눈에 띄게 초과하면, **그 경우에만** 아주 짧은 debounce(예: 30~50ms)를 입력 길이 임계값(예: 20,000자) 이상일 때만 조건부로 적용한다. 임계값 이하에서는 항상 즉시 반영해야 한다.
- 이는 `text-cleaner`가 이미 채택한 "작을 때는 즉시, 클 때만 짧게 지연" 패턴과 같은 원칙이지만, 이 도구는 계산이 훨씬 가벼우므로 기본값 자체를 debounce 없음으로 둔다.

## 9. Architect 결정 5 — 문자 수 표시: 카드 그리드 대신 한 줄 텍스트

브리핑이 "이 기능 때문에 UI가 복잡해지면 제외한다"고 명시했으므로, `text-cleaner`처럼 통계 카드 그리드를 만들지 않는다.

- 결과 영역 아래에 `입력 24자 · 결과 24자` 형태의 한 줄 보조 텍스트만 표시한다(작은 글씨, `text-muted` 톤).
- 글자 수는 UTF-16 `.length`가 아니라 code point 기준(`[...text].length`)으로 센다(이모지 등 서로게이트 쌍 문자 오카운트 방지, §5 근거와 동일).
- 표시/숨김을 위한 별도 옵션은 두지 않는다 — 항상 표시하되 시각적으로 부차적인 위치에 둔다.

## 10. Architect 결정 6 — 파일 구조: 별도 옵션/통계 모듈 없이 단일 순수 함수 파일

이 도구는 `text-cleaner`처럼 9단계 파이프라인이나 여러 옵션 조합이 없다. 파일을 과도하게 쪼개지 않는다.

```
app/[locale]/tools/korean-initial-converter/page.tsx
components/tools/korean-initial-converter/korean-initial-converter.tsx
lib/tools/korean-initial-converter/convert.ts
lib/tools/korean-initial-converter/korean-initial-converter.test.ts
tests/korean-initial-converter-browser.mjs
```

- `convert.ts`: `toInitial(codePoint)`, `convertText(text, { removeWhitespace })`, `charCount(text)` 세 개의 작은 순수 함수만 둔다. `types.ts`/`presets.ts`/`validation.ts` 같은 별도 파일은 만들지 않는다 — 옵션이 체크박스 1개뿐이라 분리할 실익이 없다.
- Web Worker는 사용하지 않는다. 계산이 O(n) 단순 순회이고 §8에서 정한 조건부 debounce로 충분히 대응 가능하므로, `screenshot-statusbar-remover`나 `screenshot-stitcher`와 달리 Worker 도입 비용을 정당화할 성능 병목이 없다.
- 도구 등록: `lib/tools/registry.ts`의 `TOOLS` 배열에 `category: "text"`로 추가한다(`word-counter`, `text-cleaner`와 같은 카테고리, `menuOrder` 3번째). 아이콘은 lucide-react `Type`을 기본 제안하되 Builder가 실제 렌더링을 보고 더 적합한 아이콘으로 바꿀 수 있다.
- i18n은 기존 프로젝트 규칙대로 **3곳** 모두 갱신한다: `Common.toolsNav.koreanInitialConverter`(메뉴), `Home.tools.koreanInitialConverter`(홈 카드), `Tools.koreanInitialConverter.*`(전체 페이지). 이전에 `privacy-redactor` 개명 시 `Common.toolsNav` 한 곳을 놓쳤던 전례가 있으므로 Builder는 완료 전 세 곳을 모두 grep으로 재확인한다.

## 11. UI 구성

매우 단순한 2블록 레이아웃(입력 → 결과), text-cleaner의 듀얼 textarea 톤을 재사용하되 옵션 패널 없이 구성한다.

- 상단 히어로: 제목 "한글 초성 변환기", 짧은 설명 한 줄(SEO 키워드 자연 포함, §13).
- 입력 영역: `<textarea>` — placeholder "변환할 텍스트를 입력하세요".
- 결과 영역: 읽기 전용 표시(결과는 입력에서 100% 파생되며 사용자가 직접 편집할 이유가 없으므로 `text-cleaner`와 달리 편집 가능하게 만들지 않는다 — 더 단순한 선택).
- 공백 제거 체크박스 1개(결과 영역 근처, 작게).
- 입력/결과 글자 수 한 줄(§9).
- 버튼: `[결과 복사]` `[초기화]`.
- 복사 성공 시 버튼 라벨이 일시적으로 "복사되었습니다"로 바뀌었다가 약 2초 후 원래 라벨로 돌아온다(`word-counter`/`text-cleaner`와 동일한 패턴). 복사 실패(클립보드 API 미지원/권한 거부)는 조용히 무시하고 버튼 상태를 되돌리지 않는다 — 별도 오류 배너를 새로 만들 만큼 무거운 실패가 아니다.
- 초기화 시 입력·결과·공백 제거 체크박스를 모두 기본값으로 되돌리고 입력 focus를 되돌린다.
- 예시 3~5개(§4 표 일부 재사용)를 결과 영역 아래 짧게 노출해 "이 도구가 뭘 하는지"를 설명 없이도 즉시 이해시킨다.

## 12. Privacy

- 입력 텍스트는 서버로 전송하지 않는다. `localStorage`/`sessionStorage` 자동 저장 없음.
- 페이지 하단 또는 입력 영역 근처에 "입력한 텍스트는 브라우저에서만 처리됩니다." 한 줄 안내를 둔다.

## 13. SEO

- 목표 검색 의도: 한글 초성 변환기, 초성 변환, 한글 초성 추출, 초성 만들기, 글자 초성 변환, 한글 자음 변환.
- `<h1>`과 메타 title/description에 "초성 변환"·"한글 초성"을 자연스럽게 포함한다. 키워드 나열은 하지 않는다.
- 도구 자체(입력/결과 영역)가 페이지 최상단에 위치해야 한다 — 다른 도구 페이지처럼 설명이 도구보다 먼저 오되, 설명은 1~2문장으로 짧게 유지한다.
- 다른 도구와 동일하게 `createPageMetadata`로 locale별 canonical/hreflang을 생성하고 `registry.ts` 등록으로 사이트맵에 자동 포함시킨다.

## 17. Architect 최종 검토

### 기존 구조와의 충돌

- Next.js App Router, TypeScript, Tailwind, next-intl 구조와 완전히 일치하며, Server page + Client 컴포넌트 + 순수 domain 함수라는 기존 패턴을 그대로 따른다.
- 서버 route·DB·외부 API가 필요 없다. 이미지 처리 도구들과 달리 Canvas/Worker/Blob 관련 인프라도 전혀 필요 없는, 프로젝트에서 가장 단순한 축의 도구다.
- `word-counter`, `text-cleaner`와 같은 "text" 카테고리에 자연스럽게 추가된다.

### 확정된 결정 요약

1. 외부 라이브러리 없이 Unicode 오프셋 계산(§5)으로 구현한다.
2. NFC 정규화는 변환 파이프라인 직전에만 적용하고 입력 state 원본은 건드리지 않는다(§6). 호환 자모(U+3131)와 결합 자모(U+1100)는 서로 다른 블록이며 별도 분기 없이 NFC + 범위 검사만으로 브리핑의 모든 예시가 성립한다.
3. 공백 제거 옵션은 스페이스류만 지우고 줄바꿈은 항상 보존한다(§7).
4. V1은 debounce 없이 즉시 반영하고, 대용량 입력에서 실측 지연이 확인될 때만 조건부로 짧은 debounce를 추가한다(§8).
5. 문자 수는 카드 그리드가 아니라 한 줄 보조 텍스트로만 표시한다(§9).
6. 파일은 `convert.ts` 단일 순수 함수 모듈로 최소화하고, Worker는 사용하지 않는다(§10).
7. 결과 영역은 읽기 전용으로 둔다(입력에서 100% 파생되므로 편집 가능하게 만들 이유가 없다) — `text-cleaner`의 "편집 가능 + 덮어쓰기 안내" 패턴은 이 도구에는 과한 복잡도라 채택하지 않는다.

### 남은 구현 위험과 통제

- 대용량 입력 시 매 keystroke 동기 계산이 버벅일 위험 — §8의 조건부 debounce로 대응하되, 먼저 실측 없이 debounce를 넣지 않는다(불필요한 복잡도 방지).
- 브리핑의 "이미 분리된 자모"와 "NFD"를 같은 것으로 오인해 잘못된 분기 코드(예: 정규식으로 호환 자모까지 억지로 재조합 시도)를 작성할 위험 — §6의 블록 구분 표로 명시해 방지한다.
